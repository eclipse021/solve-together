## 짧은 회고

### 준현

- 접근: 점수 목록을 List<Integer>[][][][]에 나눠 저장하고 정렬한 뒤, 필요한 리스트를 골라 이분 탐색했다.
- 막힌 지점:
  1. Java의 다차원 List 배열 선언 방식이 익숙하지 않았고, 문자열 파싱 과정에서 split() 사용법을 공부했다.
  2. 재귀 이분 탐색에서 재귀 호출 앞에 return을 붙이지 않아 결과가 전달되지 않는 실수가 있었다.
- 다음에 기억할 것:
  1. 다차원 List 배열은 List<Integer>[][] arr = new ArrayList[x][y]처럼 선언하고 각 칸을 new ArrayList<>()로 초기화하자.
  2. 문자열은 String[] s = str.split(" ")처럼 나눌 수 있고 결과는 String[]으로 반환된다.

### 준희

- 접근: 처음엔 언어-직군-경력-푸드를 깊이로 갖는 트리 구조를 고민. 하지만 전체 지원자를 순회하며 if 분기로 매칭하면 `O(NM)`이라 효율성 테스트(시간 초과)를 통과 못 할 거라 판단. → 지원자 1명당 만들 수 있는 16가지(2^4) 검색 조건 조합을 `product`로 미리 다 만들어 해시맵(딕셔너리)에 점수와 함께 저장해 두는 '공간을 내주고 시간을 버는' 캐싱 전략으로 선회. 각 조건별 점수 배열을 정렬해 두고, 쿼리마다 기준 점수 이상 인원을 이분 탐색(`bisect_left`)으로 구함.
- 막힌 지점: 접근 방향(조건 조합 캐싱)에 대한 힌트를 한 번 봤는데, 보고 나선 바로 풀림. 방향만 잡히면 구현 자체는 매끄러웠음.
- 다음에 기억할 것:
  1. 정렬된 배열에서 "기준 이상 개수"는 직접 mid 갱신하지 말고 `bisect_left`로 한 줄에. 구현 시간 단축 + 엣지 케이스 방지.
  2. 여러 조건의 경우의 수(2^k)는 각 조건마다 `[원래 값, '-']` 리스트를 엮어 `itertools.product`로 깔끔하게 생성.
  3. 복잡한 분기는 조건문을 늘리기보다 "모든 경우를 미리 해시맵에 매핑"해 두면 조회가 `O(1)`.
